StudyBuddy

An AI study tool for students: upload notes or a lecture recording, get summaries, quizzes and flashcards, grounded strictly in your own material, with the grounding verified in code rather than promised in a prompt.

The problem

Students revising from long lecture notes need summaries they can trust. A general-purpose chatbot happily invents a plausible definition that was never in the notes, and a student revising from an invented definition is worse off than one who never summarized at all. StudyBuddy’s core promise is on its landing page: the AI summarizes, but only from your text.

What it does

  • Accepts notes as PDF, Word, plain text or a lecture recording; audio is transcribed first, then treated like any other notes.
  • Produces summaries in the student’s choice of four lengths and eight formats: revision notes, bullets, exam prep, concepts, flashcards, Q&A and more.
  • Extracts key terms, definitions, formulae and examples; generates quizzes and flashcards from the same material.
  • Exports to PDF, Word or text for offline revision; recent summaries are also cached locally so revision works on an unreliable connection.
  • Accounts via email (with verification codes) or Google sign-in.

Keeping the AI honest

Prompt instructions alone don’t make grounding true; models drift. So StudyBuddy enforces grounding after generation, in code: 

# every AI response passes verification before the student sees it
keywords     → must literally appear in the notes (plural-aware)
definitions  → dropped unless ≥ 50% of their words overlap the source
formulae     → dropped below 60% overlap
quiz items   → must quote an evidence sentence; ≥ 70% of the
               question’s words must come from the notes
"explain X"  → refused outright when X isn’t in the notes

The model also runs at low temperature with structured JSON output, so responses are parsed, not scraped. What survives verification is what the student sees.

Living inside a free AI quota

The free Gemini tier allows the whole project roughly 20 requests a day, so the AI layer treats failure as a first-class state:

  • Errors are classified (daily quota, rate limit, overloaded, bad parameter) and only transient ones are retried, with backoff.
  • When one model’s daily quota runs out, the service falls back across a chain of Gemini models automatically.
  • Results are cached under a SHA-256 hash of the text plus the chosen options, so a shared class handout is summarized once, not once per student.
  • The SDK client is built at startup, shaving ~3.4 s off the first request.

Auth, built properly

Authentication is custom (JWT with refresh-token rotation and a blacklist), and the details are where it earns its keep:

  • Argon2 password hashing.
  • Login takes the same time whether or not the email exists (a dummy hash is checked), so the endpoint can’t be used to enumerate registered addresses.
  • Google sign-in tokens are verified server-side, audience check included; the backend never trusts the browser’s word.
  • Per-scope rate limits: 8 login attempts a minute, 20 summaries an hour.
  • Uploads are validated by file signature, not extension, so a renamed executable is rejected.

Emails (verification codes, password resets) go out through Brevo’s HTTPS API because the host blocks SMTP ports on its free plan. The kind of deployment detail that only shows up when you actually ship on free tiers.

Scale

About 14,600 lines of hand-written code: four Django apps exposing ~31 API endpoints, an admin panel with CSV/PDF reporting, eight transactional email templates, and a React 19 frontend with seven pages.

Honest limitations

  • No automated test suite yet; the verification layer is the project’s safety net, and tests are the obvious next investment.
  • Long inputs are truncated (20,000 words) rather than chunked.
  • No OCR, so scanned PDFs aren’t supported.
  • The shared AI quota is small; the product is engineered around that reality rather than pretending otherwise.
