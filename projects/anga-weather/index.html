Anga — Weather for Kenya

A weather dashboard for Kenyan counties and towns, and underneath it a Django service designed around one brutal constraint: the upstream API allows 1,000 requests a month.

Anga (Swahili for sky) shows current conditions, an hourly outlook and a 7-day forecast for 99 Kenyan counties and towns, over a backdrop that reacts to the actual weather. It was built as a take-home assessment for a software developer role at Weather AI, against their public weather API.

The problem

The provider’s free tier is limited to 1,000 requests per month, about 33 a day across every location combined. And the limit is monthly, not per-second: hit it, and the resulting 429 doesn’t clear in a minute. It clears when the 30-day window rolls over, potentially days later. A naive app that calls the API once per page view burns the entire budget in an afternoon and then inflicts a multi-day outage on itself.

The governing idea of the whole design:

# a user request does not have to become an upstream request
1 user     →  1 upstream request      ✗ naive
100 users  →  a handful per 30 min    ✓ cached + coalesced

Two facts shaped everything, both verified against the live API rather than assumed: the endpoint takes coordinates only (no place-name lookup on the free tier), and the documented rate-limit headers turned out not to exist on real responses. Quota has to be tracked another way.

Location search is served entirely from an own PostgreSQL gazetteer (47 counties and 52 towns with aliases), because the upstream API resolves coordinates only. Typing in the search box costs zero upstream quota.

Request coalescing

Fifty users requesting an uncached Nairobi at the same instant would mean fifty identical upstream calls: 5% of the month’s budget in one burst. Instead, an atomic Redis lock (SET NX EX) elects exactly one request as the leader; it calls upstream once and writes the cache, while the other forty-nine wait for its result.

This wasn’t just unit-tested; it was verified against a running server:

$ for i in $(seq 1 30); do curl -s "…/api/weather/?location=Kisumu" & done; wait
HTTP status codes returned:   30 × 200

$ curl "…/api/meta/stats/"
cache_miss                = 30
coalesce_leader           = 1
coalesce_follower_served  = 29
upstream_request          = 1   ← thirty requests, one upstream call

Two details make it correct rather than merely plausible: followers compare the cache entry’s timestamp against what existed when they started waiting, so a stale entry is never mistaken for the leader’s fresh result; and the leader releases the lock only if its token still matches, so a slow leader can’t delete a successor’s lock.

Rate-limit strategy

When upstream says you’re rate-limited, the only correct move against a monthly quota is to stop calling upstream. A retry cannot succeed and only burns budget.

  • A 429 opens a circuit breaker: every subsequent request short-circuits to cached data without touching the network.
  • A quota reserve stops upstream calls entirely once fewer than 25 monthly requests remain, so ordinary traffic can never drain the budget to zero.
  • Quota is tracked by local counting, synced against the provider’s usage endpoint at most once a day (about 3% of the budget), with an atomic claim so multiple workers don’t all pay for the same sync.
  • No retries anywhere. Transient 5xx failures back off briefly; quota exhaustion backs off until the window can plausibly have rolled over.

Honest freshness

Stale data is never presented as current. Every response carries its age, and the UI translates that honestly; the age even keeps ticking client-side, measured on a single clock so a device with the wrong time can’t skew it.

The interface

The backend classifies each WMO weather code into a small stable vocabulary (condition_group + intensity + is_day), and the frontend switches its animated backdrop, custom SVG icons and copy on that one contract. Rain animation density follows the actual measured rainfall. Everything stops under prefers-reduced-motion, and the weather is always stated in text, so the animation is decoration rather than information.

Accessibility is tested, not asserted: a contrast audit found 20 WCAG failures on bright daytime skies, so the text scrim is now solved per sky palette, and a test recomputes the real contrast for every theme, gradient stop and text step so it cannot regress. Search is a real ARIA combobox; the freshness line is an aria-live region.

Security

  • The API key lives only in the backend environment: never in the bundle, a response, a log line or an exception message. A test asserts error bodies can never contain key fragments or the upstream hostname.
  • CORS is an explicit allow-list; only GET/OPTIONS pass.
  • Location input is length-capped and charset-restricted before it can reach the cache or database; normalisation doubles as a security boundary.
  • Per-client throttling (60/min weather, 120/min search) protects the backend and, with it, the upstream quota.
  • Production refuses to start without its secrets instead of running insecurely.

Testing

222 automated tests (98 backend, 124 frontend) concentrated on the engineering behaviour: one test runs 25 real threads against the coalescing lock and asserts a single upstream call; another asserts against a captured live API response so an upstream shape change fails loudly. A mock upstream server (tools/mock_weather_api.py) exercises the whole real code path, including simulated 429s and outages, without spending quota in development.

Trade-offs, stated plainly

  • Coalescing followers block a worker thread (bounded at 12s) because the views are synchronous. Fine at this scale; an async view would remove it.
  • Without Redis the lock degrades to per-process, still far better than nothing, and local development needs no Redis at all.
  • 99 hand-picked locations, no geocoding: a deliberate consequence of the free tier.
  • Render’s free tier cold-starts the API in ~30 seconds after idle periods.
